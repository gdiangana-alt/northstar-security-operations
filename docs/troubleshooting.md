# NorthStar Security Operations — Troubleshooting

## 1. Azure Policy Blocked Microsoft Sentinel Enablement

### Failure

Microsoft Sentinel could not initially be enabled for the NorthStar Log Analytics workspace.

Azure returned a policy denial related to the mandatory `DataClassification=Internal` tagging requirement.

### Investigation

The existing NorthStar governance policy required resources within `NorthStar-Azure-RG` to contain the required classification tag.

A Sentinel-managed `Microsoft.SecurityInsights` resource could not satisfy the blanket tagging requirement, causing deployment to be denied.

### Root Cause

A governance control designed for application resources also affected a platform-managed security resource.

This demonstrated that broad deny policies can unintentionally interfere with deployment of Azure security services.

### Remediation

Policy enforcement was temporarily changed to **Do not enforce**.

Microsoft Sentinel was enabled successfully, after which policy enforcement was immediately restored to **Default**.

### Verification

The `NorthStar-SOC-Workspace` workspace was successfully connected to Microsoft Sentinel and became operational.

### Security Lesson

Governance policies should account for platform-managed resources and service-specific deployment requirements. Production policy design should use appropriate exclusions, scopes, or policy initiatives rather than routinely disabling enforcement.

## 2. Azure Activity Data Was Not Appearing in Sentinel

### Failure

The `AzureActivity` KQL query initially returned no results.

### Investigation

Azure CLI confirmed that the subscription Activity Log contained recent management operations.

This demonstrated that the telemetry existed at the source but had not yet reached the Sentinel workspace.

### Root Cause

The subscription diagnostic setting had only recently been configured. Earlier Activity Log events were not retroactively streamed into the Log Analytics workspace, and newly generated telemetry required ingestion time.

### Remediation

A subscription-level diagnostic setting named:

`NorthStar-Activity-to-Sentinel`

was configured to stream Azure Activity Log categories to `NorthStar-SOC-Workspace`.

A new controlled Azure management event was then generated after the connector was active.

### Verification

The new activity appeared in the `AzureActivity` table and was successfully retrieved with KQL.

## 3. Incorrect Azure CLI Diagnostic Settings Command

### Failure

The initial diagnostic-settings command failed with:

`KeyError: 'resource_group'`

### Root Cause

A resource-level diagnostic settings command was being used for subscription-level Azure Activity Log telemetry.

### Remediation

The configuration was changed to use the subscription-specific Azure CLI command:

`az monitor diagnostic-settings subscription create`

### Verification

The diagnostic setting was created successfully and Azure Activity telemetry subsequently reached the Log Analytics workspace.

## 4. Scheduled Detection Appeared Not to Run

### Failure

After creating the custom Sentinel scheduled analytics rule, the **Rule runs (Preview)** interface displayed no execution records.

### Investigation

The following components were independently verified:

- Azure Activity ingestion was working.
- The KQL query returned the controlled failed operation.
- The analytics rule was enabled.
- The rule frequency and lookback were configured for five minutes.
- Alert threshold was greater than zero.
- Incident creation was enabled.

The analytics rule was also disabled and re-enabled during troubleshooting.

### Resolution

Microsoft Defender subsequently displayed a Sentinel alert generated by the scheduled detection.

The alert was automatically associated with a Sentinel incident.

This demonstrated that the analytics rule had executed even though the Rule runs preview had not displayed an execution record during troubleshooting.

### Verification

The final workflow was successfully validated:

Azure Activity  
→ Log Analytics  
→ KQL Detection  
→ Scheduled Analytics Rule  
→ Alert  
→ Incident

The incident was investigated, classified as authorized security testing, and resolved.

### Security Lesson

SIEM troubleshooting should validate each stage of the telemetry and detection pipeline independently rather than relying on a single portal status or preview interface.
